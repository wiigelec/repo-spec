## Normative requirements

- `INIT-RVA-001`: The repository validation component shall execute two validation phases in order: Phase 1 (input and source) validates request schema, canonicalization, authority propagation, source repository, source commit, material-manifest schema, source paths (rejecting tree-valued entries), and key coverage. Phase 2 (staged repository and Git state) validates the complete staged repository at repository/ including output inventory (confirming no tree-valued material_index entries), copied files, direction evidence, generated templates, promoted records, provenance, handoff, content digest, Git branch, commit count, author identity, commit message, worktree cleanliness, and remote count. Staging-state record validation is not an ordinary Phase 1 or Phase 2 check; it is performed during report finalization as an ordered in-memory validation of the proposed staging-state representation before any record is written.
- `INIT-RVA-002`: Each phase shall execute checks in ascending order number within that phase, using the checks declared in the validation profile (product.validation-profile) for the corresponding applies_to scope, and shall produce a validation report conforming to the validation report specification (product.validation-report) with status values passed, failed, error, or skipped, stable failure codes from each check's declared failure_codes array, and structured evidence fields.
- `INIT-RVA-003`: After all Phase 1 and Phase 2 checks are recorded, the validation component shall perform report finalization as an ordered write operation: (a) calculate the proposed overall_status (pass when every required Phase 1 and Phase 2 check has status passed, otherwise fail); (b) construct and validate in memory a proposed final validation report and a proposed final staging-state representation carrying validation_completed equal to true, validation_overall_status equal to the proposed overall_status, the request fingerprint computed once by request intake under product.initialization-request::INIT-REQ-012 and carried unchanged by the validated request model, and the expected repository_content_digest; (c) verify request_fingerprint linkage, repository_content_digest linkage, check ordering and uniqueness, and the completed report schema; (d) write the finalized validation report durably; (e) write the finalized staging-state record durably; and (f) verify that both durable records are mutually consistent (shared request_fingerprint and repository_content_digest, and staging-state validation_completed and validation_overall_status agreeing with the completed validation result). The validation component shall not reserialize the request or recompute its fingerprint. Promotion is permitted only when a finalized validation report and a finalized staging-state record both exist, both are durably written and mutually consistent, the report validates against its schema, every required Phase 1 and Phase 2 check has status passed, and overall_status is pass. The validation component shall not proceed to the promotion stage when any required Phase 1 or Phase 2 check has status failed, error, or skipped, or when report finalization (including any write or consistency-verification step) fails.
- `INIT-RVA-004`: The validation report shall not include a check that recursively validates the report itself. Fingerprint linkage, digest linkage, check ordering, check uniqueness, proposed staging-state validation, report schema validation, serialization, and the final durable-record consistency verification are not ordinary profile checks; they are validation-component postconditions enforced during report finalization before promotion. Report finalization is an ordered write operation: calculate the proposed overall result, construct and validate the proposed validation report and proposed staging-state representation in memory, write the finalized validation report durably, write the finalized staging-state record durably, and verify both durable records are mutually consistent. The staging-state record must not claim validation_completed equal to true before the validation report has been successfully written. Report finalization failure (including staging-state schema failure, fingerprint mismatch, digest mismatch, validation-status mismatch, linkage mismatch, ordering violation, report schema failure, serialization error, or failure to durably write both records consistently) shall be recorded as a pre-promotion failure and shall prevent promotion.
- `INIT-RVA-005`: Authority validation in Version 1 is limited to exact authority propagation: the initializer shall verify that authority.granted_by is present in the request, that the provenance record request_identifier equals the same value, and that the handoff manifest records the required linkage. The initializer shall not authenticate the governing issue, consult an external authority source, or validate authority values against an undefined execution-context source.
- `INIT-RVA-006`: Before promotion, staged repository validation shall establish `product.executable-reference-closure` for the transported common validation requirement set. Failure to resolve a required repository-relative command, required executable capability, or required portable support closure shall be a required Phase 2 failure and shall prevent promotion; explicitly governed external/platform-provided dependencies remain classified outside repository-relative installation.
