## Normative requirements

- `INIT-FSD-001`: Workspace seeding shall use the explicit product identifier and supplied product-direction material (as defined by the initialization request contract) to produce preserved direction evidence files, generated skeleton documents, and an activated but empty product-specification workspace in the repository/ directory inside the staging transaction root.
- `INIT-FSD-002`: Every document produced by workspace seeding shall have lifecycle_status candidate; the component shall not invent product semantics, infer unspecified direction, supply acceptance claims, or synthesize normative requirement content.
- `INIT-FSD-003`: Foundation seeding shall read each direction_material entry declared in the initialization request as byte-exact content from the local source repository at the exact source revision; the file shall be read as raw bytes without encoding conversion, line ending normalization, or other transformation, and the full byte content of each entry shall be preserved as-is regardless of content.
- `INIT-FSD-004`: Each direction_material entry shall be assigned a positional index equal to its 0-based position in the direction_material array as received from request intake; the array order shall be preserved as the authoritative ordering key for all projection and naming decisions, and duplicate entries shall each receive their own distinct positional index.
- `INIT-FSD-005`: Direction-material projection shall place each ingested entry as a file in the staging workspace under the deterministic path product/docs/direction/evidence/{positional_index:03d}-{source_basename}, where source_basename is the exact filename portion of the entry's source path; the file content shall be the verbatim ingested bytes without any front matter, encoding conversion, line ending normalization, or other content modification.
- `INIT-FSD-006`: Each projected direction-material file in product/docs/direction/evidence/ shall be a byte-identical copy of its source Git blob; the file shall receive no YAML front matter, no newline normalization, and no encoding transformation. Metadata about each entry shall be recorded separately in product/docs/direction/manifest.json.
- `INIT-FSD-007`: When two or more direction_material entries resolve to the same source_basename, the projected filenames shall remain unique because each uses a distinct positional_index prefix; no deduplication, renaming beyond the positional prefix, or content merging shall occur.
- `INIT-FSD-020`: Foundation seeding shall produce a direction evidence manifest at product/docs/direction/manifest.json containing for each entry the positional index, original source path, source revision (as a canonical Git object identity), source blob object ID (as a canonical Git object identity), projected evidence path, byte length, and optional non-authoritative detected media type; the manifest shall be stored separately from the evidence bytes.
