## Normative requirements

- `INIT-FIN-001`: The bounded local initialization workflow shall compose the canonical lifecycle stages (request-intake, source-resolution, destination-preflight, staging-establishment, framework-installation, direction-evidence-installation, workspace-seeding, provenance-recording, handoff-assembly, git-initialization, repository-validation, promotion, and success-finalization) into one outcome at the declared destination.
- `INIT-FIN-002`: The workflow shall execute the canonical lifecycle stages in order: request-intake (validate and normalize the JSON request), source-resolution (resolve the exact local source revision), destination-preflight (preflight the destination for absent-only), staging-establishment (create transaction root with transaction/ and repository/), framework-installation (install individual framework material entries into repository/ — no bulk directory copy), direction-evidence-installation (copy direction material into repository/ as source evidence), workspace-seeding (generate candidate document skeletons from fixed templates, activate empty product-specification workspace), provenance-recording (assemble immutable origin provenance into repository/), handoff-assembly (assemble handoff manifest into repository/), git-initialization (establish deterministic Git repository inside repository/), repository-validation (validate repository/ content and Git state against the validation profile: Phase 1 input and source checks, Phase 2 repository and Git checks, then report finalization as an ordered write protocol: construct and validate the proposed validation report and proposed staging-state representation in memory with overall_status, fingerprint linkage, digest linkage, check ordering, check uniqueness, and schema validation; write the finalized validation report durably; write the finalized staging-state record durably with validation_completed true and validation_overall_status equal to the overall result; verify both durable records are mutually consistent), promotion (atomically rename repository/ to the confirmed-absent destination only when a finalized validation report exists with overall_status pass and staging-state validation during report finalization succeeds, recording outcome as not-promoted, promoted, or indeterminate), and success-finalization (confirm promotion committed, record success outcome, remove the remaining staging transaction root, and prepare caller return value).
- `INIT-FIN-003`: The workflow shall halt when any required stage fails, leave the destination unmodified until promotion, preserve the staging transaction root for diagnostics when it exists, write an execution report at transaction/execution-report.json and update the staging-state record at transaction/staging-state.json with the failed stage identity, and report the failure and staging location without authorizing arbitrary resume. A report-finalization failure (staging-state schema validation failure, staging-state fingerprint mismatch, staging-state digest mismatch, staging-state validation-status mismatch, fingerprint linkage mismatch, digest linkage mismatch, check ordering violation, check completeness violation, report schema validation failure, serialization error, failure to write both records durably, or failure of the final dual-record consistency verification when only one record or mismatched records exist) is a pre-promotion failure with the same preservation and reporting requirements.
- `INIT-FIN-004`: The initializer shall perform only standard local execution for this workflow and shall require every authority-bearing input to be explicit in the JSON request.
- `INIT-FIN-005`: The workflow shall reject named references, remote retrieval, any existing destination (including empty directories), platform or hosting operations, arbitrary staging resume, migration, and cross-device promotion before destination mutation.
- `INIT-FIN-006`: Equivalent validated JSON requests and equivalent local source revisions, as defined by the request canonicalization, content-equivalence, and canonicalization contract, shall produce equivalent repository content and handoff manifests except for the provenance record's explicitly declared initialization timestamp; local Git topology and metadata (branch name, root commit count, author identity, commit message, worktree state, and remote count) shall be equivalent, but exact tree and commit object identifiers may differ when the committed provenance timestamp varies between runs.
- `INIT-FIN-007`: The promoted repository shall conform to the generated-repository layout contract and the output inventory (product.initializer-output-inventory-v1). Every worktree path must be a fixed worktree file, a material_index entry, or a resolved dynamic family path; no prohibited path may appear. The repository shall contain installed reusable framework material (from material_index entries linked by material_key to the material manifest), product-identified direction material preserved as source evidence (from the direction-evidence dynamic family), an activated product-specification workspace preserved by Level README.md placeholder files, a provenance record, a handoff manifest, and the validated deterministic local Git state whose administrative state (.git/) is governed separately by product.local-git-repository and product.git-bootstrap-profile. Only the repository/ directory inside the staging transaction root shall become the destination; the transaction/ directory and all contents (staging-state, execution-report, validation-report) shall be discarded during success-finalization after promotion commits, in the order: confirm promotion committed, record success, then remove the staging transaction root.
- `INIT-FIN-008`: A pre-promotion failure occurs when a required stage fails before promotion begins, or when report finalization fails (including staging-state schema validation failure during in-memory validation, failure to durably write both the validation report and the staging-state record, or failure of the final dual-record consistency verification). When report finalization fails before either record is durably written, the staging transaction root is preserved for diagnostics and neither record claims a written validation result. When only one of the two records has been durably written before the failure, the staging transaction root is preserved for diagnostics including the partially written record; the workflow must not misrepresent a partially written record pair as a consistent finalized outcome. Under pre-promotion failure: the destination remains absent; the staging transaction root is preserved for diagnostics when it exists; the execution report records the failed stage identity and carries promotion_outcome = not-promoted and completion_status = failed; the staging-state record records promotion_outcome as not-promoted; the workflow returns a failure result to the caller; and no automatic retry is authorized. The execution report and staging-state record shall agree on the request fingerprint, expected destination, and promotion outcome.
- `INIT-FIN-009`: A promoted success occurs when the repository/ directory is atomically renamed to the destination and the rename call returns success. Under promoted success: the destination owns the repository content; the staging-state record records promotion_outcome as promoted; success finalization records the external success result; the remaining staging transaction root and all transaction/ contents are removed; and the workflow returns a success result to the caller. Success is externally observable when the post-rename stat of the destination confirms the renamed repository exists at the expected path.
- `INIT-FIN-010`: An indeterminate promotion occurs when the filesystem rename operation returns an error or is interrupted such that the caller cannot safely determine whether the destination owns the repository content. Under indeterminate promotion: the workflow does not report success to the caller; the staging-state record records promotion_outcome as indeterminate; the execution report carries promotion_outcome = indeterminate and completion_status = failed and agrees with the staging-state record on the request fingerprint, expected destination, and promotion outcome; the staging transaction root and transaction/ contents are preserved when accessible; no automatic retry, rollback, or cleanup is authorized without external diagnosis and manual intervention; and the caller must treat the destination as potentially inconsistent.
- `INIT-FIN-011`: A cleanup failure after successful promotion occurs when the post-rename stat confirms the destination, the success outcome is recorded, but removal of the remaining staging transaction root fails. Under cleanup failure: the repository remains successfully promoted at the destination; the workflow does not report clean success to the caller; the workflow returns a distinct promoted-with-finalization-error failure result; the staging transaction root is preserved when possible; cleanup failure must not cause the repository to be misreported as unpromoted; and the staging-state record records the canonical cleanup-failure state: `current_stage` = `success-finalization`, `failed_stage` = `success-finalization`, `completed_stages` includes `promotion` (completed) and does not include `success-finalization` (not completed), `promotion_entered` = `true`, `promotion_outcome` = `promoted`, and `cleanup_failure` = non-empty diagnostic string. No automatic rollback or retry of the failed cleanup operation is authorized. The execution report shall carry `promotion_outcome` = `promoted` and `completion_status` = `promoted-with-finalization-error`, record the promoted destination in `expected_destination`, and record the preserved staging transaction root in `staging_root`; the report shall record promotion as completed and success-finalization as failed. The execution report and staging-state record shall agree on the request fingerprint, expected destination, promotion outcome (both `promoted`), failed stage, and terminal result; the two records must not disagree about promotion.
