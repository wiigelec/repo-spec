## Normative requirements

- `INIT-FIN-001`: The bounded local initialization workflow shall compose the canonical lifecycle stages (request-intake, source-resolution, destination-preflight, staging-establishment, framework-installation, direction-evidence-installation, workspace-seeding, provenance-recording, handoff-assembly, git-initialization, repository-validation, promotion, and success-finalization) into one outcome at the declared destination.
- `INIT-FIN-002`: The workflow shall execute the canonical lifecycle stages in order: request-intake (validate and normalize the JSON request), source-resolution (resolve the exact local source revision), destination-preflight (preflight the destination for absent-only), staging-establishment (create transaction root with transaction/ and repository/), framework-installation (install framework material into repository/), direction-evidence-installation (copy direction material into repository/ as source evidence), workspace-seeding (generate candidate document skeletons from fixed templates, activate empty product-specification workspace), provenance-recording (assemble immutable origin provenance into repository/), handoff-assembly (assemble handoff manifest into repository/), git-initialization (establish deterministic Git repository inside repository/), repository-validation (validate repository/ content and Git state, write validation report to transaction/), promotion (atomically rename repository/ to the confirmed-absent destination, recording outcome as not-promoted, promoted, or indeterminate), and success-finalization (confirm promotion committed, record success outcome, remove the remaining staging transaction root, and prepare caller return value).
- `INIT-FIN-003`: The workflow shall halt when any required stage fails, leave the destination unmodified until promotion, preserve the staging transaction root for diagnostics when it exists, write an execution report at transaction/execution-report.json and update the staging-state record at transaction/staging-state.json with the failed stage identity, and report the failure and staging location without authorizing arbitrary resume.
- `INIT-FIN-004`: The initializer shall perform only standard local execution for this workflow and shall require every authority-bearing input to be explicit in the JSON request.
- `INIT-FIN-005`: The workflow shall reject named references, remote retrieval, any existing destination (including empty directories), platform or hosting operations, arbitrary staging resume, migration, and cross-device promotion before destination mutation.
- `INIT-FIN-006`: Equivalent validated JSON requests and equivalent local source revisions, as defined by the request canonicalization, content-equivalence, and canonicalization contract, shall produce equivalent repository content and handoff manifests except for the provenance record's explicitly declared initialization timestamp; local Git topology and metadata (branch name, root commit count, author identity, commit message, worktree state, and remote count) shall be equivalent, but exact tree and commit object identifiers may differ when the committed provenance timestamp varies between runs.
- `INIT-FIN-007`: The promoted repository shall conform to the generated-repository layout contract and the output inventory (product.initializer-output-inventory-v1), and shall contain only paths declared by the inventory with each path matching its declared producer, operation, type, mode, and governing specification. The repository shall contain installed reusable framework material, product-identified direction material preserved as source evidence, an activated but empty product-specification workspace, a provenance record, a handoff manifest, and the validated deterministic local Git state. Only the repository/ directory inside the staging transaction root shall become the destination; the transaction/ directory and all contents (staging-state, execution-report, validation-report) shall be discarded during success-finalization after promotion commits, in the order: confirm promotion committed, record success, then remove the staging transaction root.
