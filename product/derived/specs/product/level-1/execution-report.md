## Normative requirements

- `INIT-RPT-001`: An execution report shall be an atomic failure-diagnostic artifact that records the outcome of each lifecycle stage, any warnings or errors produced, and the overall failure status for workflows that fail before completing.
- `INIT-RPT-002`: The execution report shall be produced when the workflow fails or when cleanup after successful promotion fails. It shall distinguish completed stages from the failed stage and any pending stages not reached. The completion_status shall be failed for pre-promotion and indeterminate failures, and promoted-with-finalization-error when promotion committed but post-promotion cleanup failed. Under cleanup failure, the report shall record the promotion stage status as completed and the success-finalization stage status as failed with the cleanup failure reason in the errors array.
- `INIT-RPT-003`: The execution report shall be a single UTF-8 encoded JSON object file written at `transaction/execution-report.json` inside the staging transaction root when the workflow fails, and shall never be part of the promoted repository content.
- `INIT-RPT-004`: The execution report representation shall define the following required fields with the given JSON types: `schema_version` as a string, `request_fingerprint` as a string, `staging_root` as a string, `expected_destination` as a string, `promotion_outcome` as a string, `completion_status` as a string, and `stages` as an array of objects.
- `INIT-RPT-004a`: The `request_fingerprint` field shall link the execution report to the exact validated initialization request that produced the workflow run. It shall be the exactly 64-character lowercase hexadecimal SHA-256 value computed once by request intake from the canonical initialization request byte sequence defined by product.initialization-request::INIT-REQ-012, copied unchanged from the validated request model, and identical to the value used by the validation report and staging-state record. The execution-report producer shall not reserialize the request, recompute the digest, or derive the fingerprint from another downstream record. The `staging_root` field shall identify the preserved diagnostic staging transaction root path and may remain the original resolved path even when cleanup partially removed content. The `expected_destination` field shall record the same resolved destination path that participates in the canonical request representation.
- `INIT-RPT-004b`: The `promotion_outcome` field shall be one of the constant strings `not-promoted`, `promoted`, or `indeterminate`, matching the promotion outcome recorded in the staging-state record. The `completion_status` field shall be one of the constant strings `failed` or `promoted-with-finalization-error`. The execution report and the staging-state record shall agree on the request fingerprint, expected destination, promotion outcome, failed stage, and terminal result.
- `INIT-RPT-005`: Each `stages` entry shall define `id` as a canonical stage identifier from the lifecycle-stage vocabulary, `status` as one of `completed`, `skipped`, `deferred`, or `failed`, `warnings` as an array of strings, and `errors` as an array of strings, with `errors` listing a failure reason when `status` is `failed`.
- `INIT-RPT-006`: The report `schema_version` shall be the constant string `1`. The `completion_status` shall be one of: `failed` (pre-promotion failure or indeterminate promotion) or `promoted-with-finalization-error` (promotion committed but post-promotion cleanup failed). The required `promotion_outcome` / `completion_status` combinations are: pre-promotion failure — `promotion_outcome` = `not-promoted` and `completion_status` = `failed`; indeterminate promotion — `promotion_outcome` = `indeterminate` and `completion_status` = `failed`; cleanup failure after committed promotion — `promotion_outcome` = `promoted` and `completion_status` = `promoted-with-finalization-error`. A `promoted-with-finalization-error` completion_status shall not be misreported as a pre-promotion failure; the repository is successfully promoted. Every required terminal outcome shall be representable using only the required fields, with no undeclared fields.
- `INIT-RPT-007`: An execution report shall reject unknown fields and shall treat every field of this specification as required with no optional fields.
- `INIT-RPT-008`: The execution report shall be deterministically serialized as JSON with object keys in the order defined by the field_order property of this specification (root for top-level keys and stages for each stage entry), `2`-space indentation, no trailing whitespace except a single final newline, and shall not reorder, reformat, or reserialize captured values.
- `INIT-RPT-009`: The execution report format shall evolve by incrementing `schema_version`; consumers of `schema_version` `1` shall reject reports declaring any other version and shall not merge unknown or extra fields silently.
- `INIT-RPT-010`: When repository-validation produces a validation report with overall_status fail, the execution report shall record the repository-validation stage status as failed, record the validation report path in the errors array, and the workflow shall not proceed to promotion.
- `INIT-RPT-011`: When report finalization fails (fingerprint linkage mismatch, digest linkage mismatch, check ordering violation, check completeness violation, schema validation failure, or serialization error), the execution report shall record the repository-validation stage status as failed with the specific finalization error in the errors array. Report-finalization failure is a pre-promotion failure; the staging transaction root shall be preserved for diagnostics and the workflow shall not proceed to promotion.
- `INIT-RPT-012`: When post-promotion cleanup fails after successful promotion, the execution report shall have completion_status promoted-with-finalization-error and promotion_outcome promoted. The report shall record the success-finalization stage status as failed with the cleanup failure reason in the errors array, and shall record the promotion stage status as completed. The execution report shall record the promoted destination path in the expected_destination field and shall not misreport the repository as unpromoted. Under cleanup failure, the execution report stages shall represent: promotion as completed, success-finalization as failed, and all prior stages as completed. The staging_root field shall identify the preserved staging transaction root used for diagnostics. The execution report and staging-state record shall agree on the request fingerprint, destination, and promotion outcome (both shall record promotion as promoted) and on the terminal result (both shall record success-finalization as failed); the two records must not disagree about promotion.
