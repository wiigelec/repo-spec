## Normative requirements

- `INIT-EQV-001`: The equivalence relation shall be defined in terms of canonical forms: each accepted initialization request, local source revision, generated content entry, handoff manifest, provenance record, and local Git object shall have exactly one canonical representation, and two items shall be equivalent exactly when their canonical representations are identical.
- `INIT-EQV-002`: Canonicalization shall be a normalization onto the canonical representation: it shall retain every authoritative value verbatim, shall apply only declared, deterministic transformations, and shall never trim, coerce, reorder, deduplicate, case-fold, or otherwise alter authoritative content.
- `INIT-EQV-003`: Request canonicalization shall normalize exactly the dimensions declared by the request representation: relative destination and source repository paths resolved against the invoking process working directory, with all other request fields retained verbatim; requests differing only in the lexical spelling of a resolved path shall be equivalent when the resolved canonical forms are identical.
- `INIT-EQV-004`: Request equivalence shall require identical canonical forms of `authority`, `product.id`, `destination`, `source.repository`, and `source.revision`, and shall require `direction_material` arrays to be identical in both membership and declared order; requests differing in any of these dimensions shall not be equivalent.
- `INIT-EQV-005`: Repository file system enumerations, generation traversals, serialization order, and manifest ordering shall be driven by a declared canonical order (repository-relative path sorted deterministically, then content order stable), so that equivalent runs do not differ as a result of filesystem enumeration order.
- `INIT-EQV-006`: Repository content equivalence shall be evaluated as a deterministic tree of entries keyed by canonical repository-relative path, comparing each entry by its type (regular file, directory, or symbolic link), its byte contents for regular files, its target text for symbolic links, and its executable-bit mode for regular files.
- `INIT-EQV-007`: File access and modification timestamps, inode numbers, ownership, and other filesystem metadata shall not be part of repository content equivalence, and the initializer shall not depend on filesystem metadata for determinism.
- `INIT-EQV-012`: Direction evidence equivalence shall require that every projected evidence file in product/docs/direction/evidence/ be byte-identical to the corresponding source Git blob at the declared source revision, and that the direction evidence manifest entries match the actual evidence files and their source material without omission or mismatch.
- `INIT-EQV-015`: Repository content equivalence shall include every path declared in the output inventory (product.initializer-output-inventory-v1): every fixed worktree file, every material_index entry (each independently inventoried — no tree-valued entries), every resolved dynamic family path, and no prohibited path. Equivalence shall be evaluated on the full inventory-defined path set. Git administrative state equivalence is governed separately by product.local-git-repository.
- `INIT-EQV-013`: Duplicate direction_material entries shall each produce their own distinct evidence file with a unique positional index, and the equivalence relation shall treat two direction_material arrays as equivalent only when they have identical membership, order, and duplicate positions.
- `INIT-EQV-008`: Local source revision equivalence shall require the same exact Git object identifier (in the repository's native object format) in the same resolved source repository path, so that equivalent revisions address identical byte sequences and subtree structure.
- `INIT-EQV-009`: The initializer shall ensure content byte equivalence for regular files without line-ending translation, encoding conversion, or Unicode normalization: bytes shall be compared and produced verbatim, and nothing shall treat distinct byte sequences (including differing line endings or Unicode encodings) as equivalent.
- `INIT-EQV-010`: Git topology and bootstrap metadata (initial branch, root commit count, author and committer identities, commit message, and remote configuration) shall be equivalent across Git implementations and versions, independent of Git tool differences; tree and commit object identifiers shall be equivalent when committed variable data (the provenance initialization timestamp) is identical between runs, and may differ when committed variable data differs.
- `INIT-EQV-011`: The variables permitted to differ between equivalent outcomes shall be explicitly declared with their scope, representation, and source: the only declared variable data for the bounded workflow is the initialization timestamp recorded in the provenance record, and no other element may vary between equivalent outcomes.
- `INIT-EQV-014`: The equivalence relation shall be reflexive, symmetric, and transitive over canonical forms, and shall partition accepted requests, source revisions, and outcomes into stable equivalence classes such that membership is decidable from canonical representations alone.
