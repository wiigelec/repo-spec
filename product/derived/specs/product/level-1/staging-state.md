## Normative requirements

- `INIT-STA-001`: A staging-state record shall capture the request fingerprint, source commit, initializer identity and version, destination path, current stage identity, completed stage identities, failed stage identity (if any), repository-content digest, Git-created flag, validation-completed flag, promotion-entered flag, promotion outcome, and cleanup failure reason (or null) for the bounded local workflow.
- `INIT-STA-002`: The staging-state record shall be a single UTF-8 encoded JSON object file written at `transaction/staging-state.json` inside the staging transaction root, and shall never be part of the promoted repository content.
- `INIT-STA-003`: The staging-state representation shall define the following required fields with the given JSON types: `schema_version` as a string, `request_fingerprint` as a string, `source_revision` as an object conforming to the canonical Git object identity representation defined by product.git-object-identity, `source_repository` as a string, `initializer_version` as a string, `expected_destination` as a string, `current_stage` as a string, `completed_stages` as an object, `failed_stage` as either a string or null, `repository_content_digest` as a string, `git_created` as a boolean, `validation_completed` as a boolean, `validation_overall_status` as either a string or null, `promotion_entered` as a boolean, `promotion_outcome` as either a string or null, and `cleanup_failure` as either a string or null.
- `INIT-STA-004`: The `request_fingerprint` field shall be a deterministic hash (SHA-256 hex digest) of the canonical JSON representation of the validated initialization request; `source_revision` shall be the full canonical Git object identity representation as defined by product.git-object-identity for the source revision; `source_repository` shall be the resolved local source repository path.
- `INIT-STA-005`: The `initializer_version` field shall record the initializer version that wrote the state record; `schema_version` shall be the constant string `1`; `expected_destination` shall be the resolved absolute filesystem path of the declared destination.
- `INIT-STA-006`: The `current_stage` field shall identify the most recently entered stage as a canonical stage identifier from the lifecycle-stage vocabulary; `completed_stages` shall map each completed stage identifier to the constant string `completed`; `failed_stage` shall be the canonical identifier of the failed stage when the transaction has failed, or `null` when no stage has failed.
- `INIT-STA-007`: The `repository_content_digest` shall be a deterministic content hash (SHA-256 hex digest) of the `repository/` subtree inside the staging transaction root, computed after all generation and before Git initialization, and shall not cover any content under `transaction/`.
- `INIT-STA-008`: The `git_created` field shall be `true` when local Git initialization has completed inside `repository/`. The `validation_completed` field shall become `true` only when report finalization has successfully serialized, written, and consistency-verified the finalized validation report; the `validation_overall_status` field shall then record the overall_status value (pass or fail) from that finalized validation report. During report finalization, a proposed staging-state representation shall be constructed in memory with `validation_completed` equal to `true` and `validation_overall_status` equal to the proposed overall result, validated against this schema without writing, and written durably to `transaction/staging-state.json` only after the finalized validation report has been written. The staging-state record must not claim `validation_completed` equal to `true` before the validation report has been successfully serialized and written. The staging-state record and the validation report shall share matching `request_fingerprint` and `repository_content_digest` values.
- `INIT-STA-009`: The `promotion_entered` field shall be `true` when the promotion stage has been entered; `promotion_outcome` shall be one of the constant strings `not-promoted`, `promoted`, or `indeterminate` when promotion has been attempted and resolved, or `null` when promotion has not been entered or an attempted promotion has not been resolved. When cleanup after successful promotion fails, `promotion_outcome` remains `promoted`; the `cleanup_failure` field, not a changed promotion outcome, records the failure.
- `INIT-STA-010`: The three promotion outcomes are: `not-promoted` when promotion did not occur (pre-promotion failure or explicit abort), `promoted` when the `repository/` directory was atomically renamed to the destination and the rename call returned success, and `indeterminate` when the filesystem operation returned an error or was interrupted such that the caller cannot safely determine whether the destination owns the repository content.
- `INIT-STA-011`: The `cleanup_failure` field shall be a required nullable field that is always present in every staging-state record. When cleanup has not been attempted or when cleanup succeeds, `cleanup_failure` shall be `null`. When post-promotion staging-root removal fails after `promotion_outcome` is `promoted`, `cleanup_failure` shall be a non-empty diagnostic string describing the cleanup failure reason; the presence of a non-null `cleanup_failure` value does not change the promotion outcome. The deterministic serialized forms are: normal state — `"cleanup_failure": null`; cleanup-failure state — `"cleanup_failure": "<non-empty diagnostic string>"`. The canonical cleanup-failure staging-state is: `current_stage` = `success-finalization`, `failed_stage` = `success-finalization`, `completed_stages` includes `promotion` (completed) and does not include `success-finalization` (not completed), `promotion_entered` = `true`, `promotion_outcome` = `promoted`, and `cleanup_failure` = non-empty diagnostic string. No automatic rollback or retry of the failed cleanup operation is authorized.
- `INIT-STA-012`: The staging-state record shall reject unknown fields and shall treat every field of this specification as required with no optional fields. The `cleanup_failure` field shall be `null` when cleanup has not been attempted or succeeded, and a non-empty string when cleanup after successful promotion failed.
- `INIT-STA-013`: The staging-state record shall be deterministically serialized as JSON with object keys in the order defined by the field_order property of this specification, `2`-space indentation, no trailing whitespace except a single final newline, and shall not reorder, reformat, or reserialize captured values.
