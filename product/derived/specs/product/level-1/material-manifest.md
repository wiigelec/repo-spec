## Normative requirements

- `INIT-MMF-001`: The maintained material manifest shall be a single UTF-8 encoded JSON file at `product/scripts/initializer/framework-inventory.json` in the source repository, declared with schema_version and an entries array.
- `INIT-MMF-002`: Each manifest entry shall be a JSON object defining: `material_key` (a stable unique identifier that links to the output inventory's material_index), `source_path` (repository-relative source path), `role` (one of the material role classifications), `operation` (one of the supported operations), `source_type` (the expected Git object type: blob or symlink; tree is not permitted for the Version 1 bounded local workflow), `mode` (the expected Git mode string such as 100644 or 100755), and optional `profile` and `exclusion_rationale`.
- `INIT-MMF-003`: The manifest shall support at least the following operations: `copy-verbatim` (destination bytes equal source Git blob bytes with no encoding or newline changes, source commit and path recorded, mode follows the declared policy, filesystem timestamps do not participate), `instantiate-template` (destination produced from an exact template with only declared substitution fields permitted, defined escaping rules, canonical serialization, and explicit behavior for missing fields), and `generate-record` (destination produced by serializing a governing schema from source fields using canonical field order and canonical JSON encoding).
- `INIT-MMF-004`: The manifest shall not rely on broad recursive directory copying as the authority for any path; every output path shall have exactly one material_index entry in the output inventory, and the material manifest provides the source resolution for that entry via material_key. Overlapping or duplicate material_key values shall be rejected as invalid.
- `INIT-MMF-005`: Source paths in the manifest shall be interpreted relative to the root of the source commit tree.
- `INIT-MMF-006`: The manifest schema_version shall be the constant string `1` for this version; future versions shall increment schema_version and shall not silently merge unknown entry fields.
- `INIT-MMF-007`: Every material manifest entry whose operation is copy-verbatim shall have a material_key that matches exactly one material_index entry in the output inventory (product.initializer-output-inventory-v1). The material manifest shall not independently declare output paths; it resolves source information for output paths already declared by the output inventory.
- `INIT-MMF-008`: Every material_key in the material manifest shall have a corresponding material_index entry in the output inventory. Unused material_key values (present in the material manifest but absent from the output inventory) shall be rejected. Every output inventory material_index entry shall have a corresponding material_key in the material manifest. The mapping is one-to-one and bidirectional for copy-verbatim entries.
- `INIT-MMF-009`: No material-manifest entry with source_type tree shall be accepted. Every source_path in the material manifest must resolve to a Git blob (regular file) or symlink in the source commit tree. A source_path that resolves to a Git tree object (directory) is invalid because it would make the set of output paths depend on source-directory contents rather than the closed output inventory.
- `INIT-MMF-010`: Every material-manifest entry with operation copy-verbatim shall have source_type blob or symlink. An entry with source_type tree and operation copy-verbatim is undefined and shall be rejected before installation.
- `INIT-MMF-011`: No material-manifest entry may be interpreted as an installation unit for a source subtree. Every entry declares exactly one source_path that resolves to one Git blob or supported symlink. Undeclared source-directory descendants shall not be installed.
