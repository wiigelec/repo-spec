# Risks and unresolved decisions

Status: candidate; non-authorizing

## Risks

| Risk | Description | Impact | Controls and evidence | Trigger and owner |
| --- | --- | --- | --- | --- |
| R1: Existing-code drift | Implementation and tests predate or conflict with accepted product specifications. Passing tests encode superseded behavior and may pass when they should fail. | False conformance confidence; silent acceptance of non-conforming behavior in successor implementation. | B0 baseline must explicitly classify every composite key. No classification by file presence or all-tests-pass alone. Every `preserve` claim must cite specific observable accepted behavior and protecting test. | Owner: B0 governed issue. Closed when B0 matrix exists and no undifferentiated classification remains. |
| R2: Orchestration size | I5 composes 13 canonical stages, cross-increment identity propagation, preconditions, promotion gates, and four terminal outcomes in a single orchestrator. | Complexity may hide sequencing defects or missing failure-path coverage. | I5 E2E evidence must cover all four terminal outcome classes plus determinism and rejection. Focused component evidence for each stage exists in predecessor increments. No orchestrator may redefine product semantics. | Owner: I5 governed issue. Closed when all terminal boundaries have fault-injection E2E evidence. |
| R3: Filesystem transaction and promotion correctness | Atomic rename, post-rename commitment detection, indeterminate rename, cleanup failure, and same-filesystem isolation depend on OS/filesystem behavior not controlled by Python. | Silent data loss, partial promotion, or unrecoverable staging on rare filesystem states. | Fault-injection evidence at every finalization write and rename boundary. Pre-rename destination-absence recheck. Post-rename stat confirmation. No copy/fallback/retry. | Owner: I4 governed issue. Refresh when supported platform combinations change. |
| R4: Future-extension scope leakage | Implementation or tests may inadvertently support platform profiles, dry-run, resume, recovery, or remote retrieval, creating undeclared V1 capabilities. | Implementation may exceed accepted scope, making future-extension acceptance harder and creating hidden dependencies. | I1 must reject every unsupported profile and excluded behavior before mutation. E2E rejection evidence covers all six excluded future-extension domains. No V1 path accepts platform, remote, dry-run, resume, recovery, or migration input. | Owner: I1 and I5 governed issues. Refresh on each spec-acceptance cycle. |
| R5: Plan and correspondence drift after specification changes | A material acceptance, revision, or retirement affecting any accepted specification that this plan relies upon invalidates the corresponding plan sections. | Implementation proceeds under obsolete authority; correspondence claims no longer match accepted specs. | `repo.development-workflow` and `repo.implementation-plan` require material-specification impact review. This plan records the exact accepted base (`d3cf252`) and each controlling spec. | Owner: any governing issue or PR that accepts a specification revision. Closed only after plan impact review. |
| R6: Duplicate bare requirement IDs | `INIT-FIN-001` through `INIT-FIN-008` appear in both `product.framework-installation` and `product.full-initialization`. | Bare-ID traceability is ambiguous; misassignment could invent or omit product semantics. | All traceability in this plan uses composite `<spec_id>::<requirement_id>` keys. B0, gates, and successor issues must preserve composite identity. | Owner: Patch 1, carried through all successor governed work. Closed when bare-ID ambiguity is eliminated through specification repair (separate governed work). |
| R7: Accepted provenance conflict | `product.provenance-recording::INIT-PRC-001` requires capture of values the provenance-record contract cannot encode. | Blocked I3, I4, and I5 authorization; no complete plan acceptance or implementation derivation until repaired. | Conflict is recorded at every affected increment boundary. No plan section chooses omission, extra fields, alternate record, or other semantic resolution. | Owner: separate governed specification-repair issue. Condition for I3/I4/I5 unblocking. Refresh after accepted repair and required plan impact review. |
