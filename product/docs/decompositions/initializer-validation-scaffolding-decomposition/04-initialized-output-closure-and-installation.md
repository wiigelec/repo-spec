# Initializer Validation Scaffolding Decomposition: Initialized-Output Closure and Installation

> Part 4 of 4 · [Initializer validation scaffolding decomposition index](../INITIALIZER-VALIDATION-SCAFFOLDING-DECOMPOSITION.md) · [Previous](./03-product-test-lifecycle.md)

## Status

Directional decomposition content.

## Purpose

Bound initializer responsibility for installing a fresh repository whose transported common validation workflow can resolve every required repository-relative command through stable installed interfaces without manual post-initialization repair.

## Responsibilities

Ensure the initializer output contains the stable validation/test interfaces and supporting installed material required by transported common CI.

Preserve executable-reference/output closure: each required repository-relative command invoked by the transported validation workflow must resolve in initialized output unless the dependency is explicitly external or platform-provided under accepted authority.

Keep stable installed interfaces separate from repo-spec source-development-only test implementation, so satisfying closure does not imply copying the complete repo-spec development test tree.

Coordinate closure with the honest zero-applicable product-test lifecycle: the generic product-test interface remains present and behaves according to later normative semantics even when no governed product implementation tests are applicable.

Define the stopping boundary for this decomposition: exact closure proof, installation mechanics, diagnostics, compatibility, and upgrade propagation move to normative product specification work before implementation planning.

## Boundaries

This area covers initializer installation responsibility, required-command closure, installed-support boundary, first-push usability outcome, and directional failure visibility when closure cannot be established.

It does not decide exact generation inventory, copy rules, manifest schema, closure algorithm, filesystem layout beyond existing repository authority, wrapper implementation, command behavior, or upgrade reconciliation mechanics.

## Dependencies

This area depends on all prior areas: stable workflow/interface ownership identifies required surfaces; validation self-test ownership identifies portable installed self-test responsibilities; product-test lifecycle identifies the generic product-test surface and legitimate zero-applicable state.

Likely downstream specification work may include Level 1 installed-command requirement identity, Level 2 executable-closure/installability capability, and, only if required, Level 3 coordination of the complete fresh-repository validation-scaffolding outcome.

Compatibility with later derived-repository upgrade work is cross-cutting and must be specified without silently changing the separately accepted initializer-upgrade decomposition.

## Exclusions

This area does not mutate initializer runtime, framework inventory, common workflow, validators, test scripts, `wiigelec/test-repo`, release behavior, or upgrade implementation.

It does not require transport of repo-spec's complete source-development test tree and does not define exact fail-closed mechanics or diagnostic wording.

## Unresolved decisions

Exact installed-command inventory representation, external/platform dependency classification, closure-check algorithm, generation-time versus validation-time enforcement, failure classification, diagnostics, support-library installation, compatibility rules, upgrade propagation, and proof/evidence format remain unresolved.

Later specification work must determine whether existing initializer inventory/generation specifications can be extended or whether new Level 1-3 product specifications are required.

## Successor work

Create or revise and accept the owner-appropriate normative product specification set for the four decomposition areas, including exact closure and lifecycle contracts needed before implementation planning.

Exact specification identifiers, dependency edges, reuse decisions, compatibility semantics, and whether a Level 3 complete lifecycle specification is required remain for that governed successor work. Implementation planning is not authorized until the necessary controlling specifications are accepted.
