## Normative requirements

- `REPO-WF-001`: The repository shall require a governing issue, an isolated branch, validation, push, and PR for bounded changes.
- `REPO-WF-003`: When starting a bounded change, the chatbot shall inspect the user request, current branch, open PRs, repository records, and hosting-platform state for an existing governing issue; if exactly one open issue governs the requested work, it shall be reused; if none exists, the chatbot shall create one before any branch is created; if multiple issues could govern the work or the issue does not clearly authorize it, the chatbot shall stop and ask for clarification without creating a duplicate issue.
- `REPO-WF-004`: The chatbot shall determine the intended branch from the governing issue and the convention issue-<number>-<short-slug>, search local and remote refs for that branch, verify an existing branch corresponds to the governing issue and its recorded base, and reuse it only if its commits and working-tree changes remain within scope and will not overwrite or mix unrelated work; if no valid branch exists, the chatbot shall create it from the exact accepted base recorded for the issue.
- `REPO-WF-005`: The chatbot shall report whether the issue and branch were reused or created, along with the issue number, accepted base, current branch, scope, exclusions, and next authorized action.
- `REPO-WF-006`: When creating or updating a GitHub issue or pull request body, the chatbot shall pass the body as a literal Markdown payload or file contents and shall not allow shell interpolation, command substitution, or concatenated command output to alter the intended Markdown structure.
- `REPO-WF-007`: The normative development lifecycle for governed development shall be: collection, analysis, candidate functional set, approved functional set, accepted decomposition, accepted owner-appropriate normative specifications, accepted implementation plan, governed implementation issues, and maintained artifacts. Repository/framework-owned development shall use accepted repository specifications for repository-generic requirements; product-owned development shall use accepted product specifications in the applicable Level 0–3 dependency order. Collection and analysis shall precede candidate functional-set formation, an approved functional set shall be required before the corresponding decomposition may be accepted, and each later acceptance-bearing stage shall require acceptance of its predecessor stage before the next stage may be accepted, unless a later stage's governing specification explicitly permits concurrent drafting without acceptance.

- `REPO-WF-010`: Before an implementation plan is accepted, every applicable controlling specification shall satisfy the plan contract required by repo.implementation-plan and remain consistent with the accepted authority the plan claims to realize; repo.implementation-plan owns detailed plan-invalidity semantics.

- `REPO-WF-013`: A material specification change, including revision, supersession, or retirement of an accepted specification that an implementation plan relies upon, must trigger an implementation-plan impact review. - `REPO-WF-014`: A material implementation-plan change (including sequencing or scope changes) must be reflected in the controlling plan before affected open governing issues are updated. Completed implementation must be audited when controlling authority changes materially, and the audit results must be recorded before successor implementation proceeds.
- `REPO-WF-015`: The repository may classify explicitly exploratory experiments that are outside maintained artifact scope. An exploratory experiment shall be isolated from maintained paths where practical, shall not claim conformance, acceptance, release, or maintained-artifact status, shall not silently become maintained implementation, shall require a later governed specification and implementation process before adoption, and shall have explicit disposal, archival, or adoption criteria. Adoption of experimental work shall require the applicable accepted owner-appropriate normative specifications and an accepted implementation plan before maintained implementation may begin.
- `REPO-WF-016`: Implementation authorization shall be derived from the accepted governing issue together with controlling specification and plan authority; this workflow shall not duplicate the governing issue's canonical evidence-field contract.
- `REPO-WF-017`: Before any governed repository mutation, the actor shall read the repository README, discover the authoritative repository-spec manifest, read repo.authority-model and repo.development-workflow, and then load every additional accepted specification applicable to the planned change.
- `REPO-WF-018`: Before any repository mutation, workflow initialization shall discover an existing governing issue or create one only when authorized by REPO-WF-003, then identify and read the resulting governing issue.
- `REPO-WF-019`: Before any repository mutation, workflow initialization shall load only the relevant overview, decomposition, plan, specification, and predecessor records needed to establish controlling authority and bounded work context.
- `REPO-WF-020`: Before any repository mutation, workflow initialization shall inspect the actual Git branch, open pull requests, accepted base, working tree, remote state, and hosting-platform state.
- `REPO-WF-021`: Before any repository mutation, workflow initialization shall verify that the branch recorded in the accepted default-branch base is the repository's actual current default branch.
- `REPO-WF-022`: Before any repository mutation, workflow initialization shall report the governing issue, controlling authority, accepted base, intended branch, scope, exclusions, dependencies, next authorized action, and unresolved authority conflicts.
- `REPO-WF-023`: Workflow initialization shall stop when controlling authority is missing or conflicting, except that absence of a governing issue shall follow the explicit discovery-or-create procedure in REPO-WF-003.
