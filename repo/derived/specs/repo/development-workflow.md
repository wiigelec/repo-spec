## Normative requirements

- `REPO-WF-001`: The repository shall require a governing issue, an isolated branch, validation, push, and PR for bounded changes.
- `REPO-WF-002`: Before any repository mutation, the chatbot shall initialize by reading README.md, discovering the authoritative manifest, reading the accepted development-workflow specification, discovering an existing governing issue or creating one when authorized by REPO-WF-003, then identifying and reading the resulting governing issue, loading only relevant overview, decomposition, plan, specification, and predecessor records, inspecting the actual Git branch, open pull requests, accepted base, working tree, remote state, and hosting-platform state, verifying that the branch recorded in the accepted default-branch base is the repository's actual current default branch, reporting the governing issue, controlling authority, accepted base, intended branch, scope, exclusions, dependencies, next authorized action, and unresolved authority conflicts, stopping when controlling authority is missing or conflicting except that absence of a governing issue shall follow the explicit discovery-or-create procedure in REPO-WF-003, and withholding mutation until initialization is complete.
- `REPO-WF-003`: When starting a bounded change, the chatbot shall inspect the user request, current branch, open PRs, repository records, and hosting-platform state for an existing governing issue; if exactly one open issue governs the requested work, it shall be reused; if none exists, the chatbot shall create one before any branch is created; if multiple issues could govern the work or the issue does not clearly authorize it, the chatbot shall stop and ask for clarification without creating a duplicate issue.
- `REPO-WF-004`: The chatbot shall determine the intended branch from the governing issue and the convention issue-<number>-<short-slug>, search local and remote refs for that branch, verify an existing branch corresponds to the governing issue and its recorded base, and reuse it only if its commits and working-tree changes remain within scope and will not overwrite or mix unrelated work; if no valid branch exists, the chatbot shall create it from the exact accepted base recorded for the issue.
- `REPO-WF-005`: The chatbot shall report whether the issue and branch were reused or created, along with the issue number, accepted base, current branch, scope, exclusions, and next authorized action, and shall not mutate repository source until the governing issue and issue branch have been discovered or created and verified.
- `REPO-WF-006`: When creating or updating a GitHub issue or pull request body, the chatbot shall pass the body as a literal Markdown payload or file contents and shall not allow shell interpolation, command substitution, or concatenated command output to alter the intended Markdown structure.
- `REPO-WF-007`: The normative development lifecycle for governed development shall be: collection, analysis, candidate functional set, approved functional set, accepted decomposition, accepted owner-appropriate normative specifications, accepted implementation plan, governed implementation issues, and maintained artifacts. Repository/framework-owned development shall use accepted repository specifications for repository-generic requirements; product-owned development shall use accepted product specifications in the applicable Level 0–3 dependency order. Collection and analysis shall precede candidate functional-set formation, an approved functional set shall be required before the corresponding decomposition may be accepted, and each later acceptance-bearing stage shall require acceptance of its predecessor stage before the next stage may be accepted, unless a later stage's governing specification explicitly permits concurrent drafting without acceptance.
- `REPO-WF-008`: An approved functional set must be approved before the corresponding decomposition may be accepted. No additional development-document gate exists between functional-set approval and decomposition.
- `REPO-WF-009`: A decomposition must be accepted before the controlling owner-appropriate normative specification set for the corresponding implementation scope may be finalized and accepted.
- `REPO-WF-010`: All owner-appropriate normative specifications necessary to govern a planned implementation scope must be accepted before the corresponding implementation plan may become accepted. An implementation plan whose required controlling specifications are missing, merely placeholder scaffolding, candidate where acceptance is required, structurally invalid, mutually contradictory, absent from the applicable authoritative manifest, or missing correspondence or dependency declarations required by the governing specification contracts shall not be accepted.
- `REPO-WF-011`: Before any source mutation that creates or modifies maintained artifacts, workflow initialization shall verify that the applicable accepted owner-appropriate normative specifications exist for the planned implementation scope. Initialization shall stop before source mutation when applicable specifications are missing or their acceptance status conflicts with the planned work.
- `REPO-WF-012`: Code, tests, schemas, templates, generated output, and prior implementation behavior shall not become normative authority merely because they exist. Accepted repository specifications define repository-generic normative semantics, and accepted product specifications define product-specific normative semantics within their respective authority domains.
- `REPO-WF-013`: A material specification change, including revision, supersession, or retirement of an accepted specification that an implementation plan relies upon, must trigger an implementation-plan impact review. Affected plan sections must be revised or explicitly reaffirmed before implementation under the changed authority may proceed. Implementation must pause where the accepted specification and plan no longer agree.
- `REPO-WF-014`: A material implementation-plan change (including sequencing or scope changes) must be reflected in the controlling plan before affected open governing issues are updated. Completed implementation must be audited when controlling authority changes materially, and the audit results must be recorded before successor implementation proceeds.
- `REPO-WF-015`: The repository may classify explicitly exploratory experiments that are outside maintained artifact scope. An exploratory experiment shall be isolated from maintained paths where practical, shall not claim conformance, acceptance, release, or maintained-artifact status, shall not silently become maintained implementation, shall require a later governed specification and implementation process before adoption, and shall have explicit disposal, archival, or adoption criteria. Adoption of experimental work shall require the applicable accepted owner-appropriate normative specifications and an accepted implementation plan before maintained implementation may begin.
- `REPO-WF-016`: A product-artifact governing issue that creates or modifies maintained product artifacts shall cite the accepted implementation plan, identify one or more stable workstream or stage identifiers from that plan for its bounded implementation scope, cite the applicable accepted product specifications equal to the union of the selected workstreams' or stages' controlling sets, cite the exact accepted default-branch base, and cite predecessor implementation evidence.
